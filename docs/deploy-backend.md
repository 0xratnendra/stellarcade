# Deploying the Backend (Render)

The backend — Express API, the RNG **oracle worker** and the coin-flip
**indexer worker** — runs as one Render web service built from
`backend/Dockerfile`, backed by Render Postgres and Render Key Value (Redis).
Everything except secrets is declared in
[`deploy/backend/render.yaml`](../deploy/backend/render.yaml).

Operational procedures for when this deployment breaks live in
[runbook.md](runbook.md).

## What the Blueprint creates

| Resource | Render type | Name | Notes |
| --- | --- | --- | --- |
| API + workers | web service (`runtime: docker`) | `stellarcade-api` | builds `backend/Dockerfile`, health check `GET /api/health` |
| PostgreSQL | database | `stellarcade` | injected as `DATABASE_URL` (internal address) |
| Redis | Key Value | `stellarcade-redis` | internal only (`ipAllowList: []`), injected as `REDIS_URL` |

Also set by the Blueprint: `ORACLE_ENABLED=true`, `INDEXER_ENABLED=true`,
`STELLAR_NETWORK=testnet`, testnet Horizon/RPC URLs, `PORT=10000` (Render's
default; the API binds `process.env.PORT`).

## One-time setup

Prerequisites:

- A Render account that can create Blueprints for this repository.
- Contracts deployed on testnet — `scripts/deploy-contracts.sh` writes their
  IDs to `deployments/testnet.json`.
- The `oracle` keypair: `ORACLE_SECRET_KEY` must be the secret key of the
  address passed as `--oracle` to `random-generator init`.

Steps:

1. Render Dashboard → **New → Blueprint** → connect this repository.
2. Set **Blueprint Path** to `deploy/backend/render.yaml`. Render otherwise
   looks for `render.yaml` at the repository root, which this repo does not
   use.
3. Fill in the prompted variables (the `sync: false` list below).
4. **Deploy Blueprint** and wait for the first deploy to finish.

| Variable | Where the value comes from |
| --- | --- |
| `ORACLE_SECRET_KEY` | secret key of the `oracle` keypair (never commit it) |
| `CORS_ORIGINS` | comma-separated web origins, e.g. `https://your-app.vercel.app` |
| `COIN_FLIP_CONTRACT_ID` | `jq -r .contracts.coinFlip deployments/testnet.json` |
| `RANDOM_GENERATOR_CONTRACT_ID` | `jq -r .contracts.randomGenerator deployments/testnet.json` |

`JWT_SECRET` is generated by Render itself (`generateValue: true`) and is
never written into the repository.

## Migrations

Two layers apply `npm run migrate`, so no deploy ships without schema
migrations:

1. **Pre-deploy** — the Blueprint sets `preDeployCommand: npm run migrate`,
   which runs after the image builds and before the new version takes
   traffic. This requires a paid web-service plan; if you deploy on a free
   plan, delete that line (the container then migrates at boot instead).
2. **Container start** — `backend/Dockerfile` runs
   `npm run migrate && exec node src/server.js`, so every boot (including
   `docker-compose up`) applies pending migrations before the API listens.

Keep the service at its default single instance: two instances booting at
once would race the migration.

## Verify the deployment

```bash
API=https://<service>.onrender.com/api
curl -s $API/health
curl -s $API/health/deep
```

Real output from running this image locally:

```text
$ curl -s $API/health
{"status":"Operational","timestamp":"2026-10-21T03:24:29.842Z","service":"stellarcade-api"}

$ curl -s $API/health/deep
{"status":"healthy","timestamp":"...","dependencies":{"db":{"status":"healthy",...},"redis":{"status":"healthy",...},"stellar":{"status":"healthy",...}},"soroban":{"status":"healthy",...},"contracts":{"coinFlip":{"status":"ok"},"randomGenerator":{"status":"ok"}}}
```

`health/deep` gives each dependency a 5-second budget. On a slow testnet RPC
it can answer `degraded` with HTTP 503 — retry once before treating that as an
outage (see [runbook.md](runbook.md)). With no contract IDs configured the
contract checks honestly report `not_configured` (HTTP 200 `healthy`).

With the workers enabled, also check their logs (Render Dashboard → Logs):
`oracle.worker` / `indexer.worker` should log their poll cycles, not
configuration errors.

## Day-2 operations

- **Redeploy**: pushes to the linked branch auto-deploy (Blueprint default).
  Roll back from the Render Dashboard → Deploys.
- **Contract redeploy**: contract IDs are not derived from the repo — after
  re-running `scripts/deploy-contracts.sh`, update `COIN_FLIP_CONTRACT_ID` and
  `RANDOM_GENERATOR_CONTRACT_ID` in the Blueprint/dashboard and redeploy.
- **Workers**: toggle `ORACLE_ENABLED` / `INDEXER_ENABLED` in
  `deploy/backend/render.yaml` (or the dashboard) and sync.
- **Secrets**: `ORACLE_SECRET_KEY`, `JWT_SECRET`, `CORS_ORIGINS` live only in
  Render; nothing secret is committed. Rotate them from the dashboard.
- **Incidents**: follow [runbook.md](runbook.md).

### Rotate the oracle key

Rotate `ORACLE_SECRET_KEY` if the key may have leaked (it signs every
resolution) — or periodically as hygiene. There is no on-chain setter for it:
`random-generator init(admin, oracle)` runs once and `coin-flip` pins its
`rng_contract` at init, so a new oracle address means a **full contract
redeploy**, not a Render env edit. Details: [runbook.md § oracle
compromise](runbook.md#oracle-key-compromised).

1. Pause betting on the current stack and stop the oracle worker
   (`ORACLE_ENABLED=false`) so nothing new resolves with the old key. The
   pause/unpause commands are in the runbook.
2. Generate the new keypair (or reuse a fresh `stellar keys generate oracle`).
3. Redeploy both contracts with `scripts/deploy-contracts.sh`, passing the new
   address as `--oracle` to `random-generator init`, then authorize coin-flip,
   fund the house and commit seeds over the API/worker as usual.
4. In the Render dashboard set `ORACLE_SECRET_KEY` (new secret),
   `RANDOM_GENERATOR_CONTRACT_ID` and `COIN_FLIP_CONTRACT_ID` (new IDs), turn
   `ORACLE_ENABLED=true` back on, and redeploy.
5. Unpause play only after `GET /api/health/deep` reports `contracts` `ok` for
   the new IDs and the logs show the oracle worker polling the new contracts.
   The old contracts (and their funds) are abandoned, not migrated — that is a
   property of the contracts, not of this deployment.

Nothing in the repository contains the secret; `jq -r .contracts.*
deployments/testnet.json` only yields public contract IDs.

### Read logs

Render Dashboard → the `stellarcade-api` service → **Logs**. The stream mixes
the API, `oracle.worker` and `indexer.worker`; the logger prints one line per
entry as `<timestamp> <level>: [correlationId] <message>`, and the worker
messages name their own stage. Useful filters (Render's log view supports
plain-text search):

| Looking for | Search for |
| --- | --- |
| Oracle poll cycles / resolutions | `oracle.worker` or the resolution tx hash |
| Indexer ingestion problems | `indexer.worker`, `ingestion` or `failed` |
| Request problems | the `correlationId` returned in the API error envelope |
| Startup/config errors | `ORACLE_ENABLED`, `INDEXER_ENABLED`, `not configured` |

Set `LOG_LEVEL=debug` in the dashboard to see every poll iteration; keep
`info` in normal operation (debug lines reveal wallet addresses). Winston
writes JSON to `logs/combined.log` and errors to `logs/error.log` inside the
container, but those files are ephemeral on Render — the dashboard stream is
the source of truth, and `docker logs <container>` when running the image
locally.


## Local smoke test (optional)

Builds the exact image Render builds and checks migrations + health without
touching Render:

```bash
docker build -t stellarcade-api:local backend/
docker run --rm -p 10000:10000 \
  -e PORT=10000 \
  -e DATABASE_URL=postgres://user:pass@host:5432/stellarcade \
  -e REDIS_URL=redis://host:6379 \
  -e JWT_SECRET=local-only \
  -e ORACLE_ENABLED=false -e INDEXER_ENABLED=false \
  stellarcade-api:local
curl -s localhost:10000/api/health
```

## Not automated here

This repository's CI does not deploy to Render: creating the account-owned
Blueprint and the first deploy are manual dashboard steps performed by a
maintainer with the credentials above.
